```
└──────────────────────────────── invoke() / events ──────────────────────────────────┘
┌──────────────────────── Tauri app (src-tauri/, Rust) ───────────────────────────────┐
│ lib.rs: commands · worker.rs: thread that owns the adapter, recovery, reconnection  │
│ recorder.rs: recording · portable.rs: portable version, WebView2 notice, screen on  │
│ blackbox.rs: black box (memory, files of the automatic fault recordings)            │
└─────────────────────────────────────────────────────────────────────────────────────┘

│ interpret · session (CSV/JSON) · report · health (freezes and dropped connection)  │
│ blackbox (black box: last minutes and new faults)                                  │

│ pid · dtc · vin · readiness · mode06 · maker (decoders)                             │
│ response                             (text cleaning + CAN ISO-TP frames)            │
│ elm327                               (clone-tolerant ELM327 protocol)               │
│ transport: serial (USB/BT COM) · ble (Bluetooth LE) · tcp (Wi-Fi) · simulator       │
└─────────────────────────────────────────────────────────────────────────────────────┘
```

## Main decisions

- **Core separate from the interface.** `obd-core` does not depend on Tauri: it can be tested with `cargo test -p obd-core --all-features` on any system, without the graphics libraries Tauri asks for, and reused (command line, another app).
- **One `Transport` interface for all connections.** It only moves bytes (`write_all`, `read` with a timeout). BLE (`btleplug`, asynchronous) has a small internal Tokio runtime and exposes the same blocking interface; it picks the write characteristic and the notification characteristic by itself (services FFF0, FFE0, 18F0 or any other with those properties). It sits behind the core's `ble` feature.
- **The simulator is a transport.** Demo mode receives the same text commands as a real ELM327 and answers the same way, so it tests the whole program. With `quirky` it imitates clones (an echo that won't turn off, `SEARCHING...`, null bytes, refused AT commands).
- **Clone tolerance.** Configurable timings; `OK` and the echo are never required; unsupported AT commands (`?`) are ignored and listed in `AdapterInfo::unsupported_at`; an answer without `>` is still used; automatic serial speed (38400, 9600, 115200...); lost or interrupted OBD requests (`STOPPED`, `BUFFER FULL`, bus error) are repeated once, with an `ATI` before to unfreeze the adapter (a lone CR would make the ELM327 repeat the last command); plan B of trying protocols one by one; reading several PIDs per request with an automatic fall back to one at a time.
- **Long answers from several control units.** With headers off (`ATH0`), two control units sending long answers at the same time (engine and transmission on `03` or `0902`) arrive mixed up and cannot be told apart. `response::has_interleaved_frames` notices this (a new length before the previous one ends); then `Elm327::request` asks again with `ATH1`, joins the frames of each control unit with `assemble_can_with_headers` and goes back to `ATH0`.
- **One thread owns the adapter.** Serial ports cannot be used from two places. The interface's commands become tasks in the thread's queue and run between the live readings, without freezing the window.
- **Connection health separate from recovery.** `health.rs` only classifies each answer (valid, suspicious, adapter restart, connection lost) and decides the action; `Elm327::recover` restarts and reconfigures the adapter on the already known protocol; `worker.rs` reopens the port with growing waits (up to 3 min), using a `Reopen` function created in `connect` with the same port, speed and protocol; on a USB adapter it keeps the USB identity (`serial::usb_identity`) and, if the old port fails, looks for the same adapter on a new COM port (`serial::find_usb_port`). During reconnection the old port is closed (`transport::Closed`), because Windows does not let the same COM port be opened twice. The simulator imitates the failures (`ATSIMHANG`, `ATSIMRESET`, `ATSIMFREEZE`, `ATSIMDROP`).
- **Tools that change the adapter's settings always put it back as it was.** The compatibility test (`adapter_test.rs`) and the control unit search (`ecu_scan.rs`, which turns headers on with `ATH1` and changes the target with `ATSH`) end with `Elm327::reconfigure` (ATZ, the configuration and the already known protocol). No command that writes to the adapter's memory (`ATPP`, `ATCV`, `ATSD`, `ATBRD`) and no service that writes to the control unit (UDS 0x2E, 0x31, 0x27...) is used: read-only (OBD modes 01/09 and UDS 0x22).
- **Manufacturer parameters (pilot).** `maker.rs` reads `data/maker_params.json`, generated by `tools/obdb_import.py` from OBDb (CC BY-SA 4.0): for each model, the 21/22 requests, the control unit's address and how to extract each value from the answer (start bit, size, scale, unit already converted to the metric system). The importer only accepts read requests that do not need a diagnostic session, an extended address or another CAN priority. The keys start with `mfr_` and enter the live reading like any other: `worker.rs` groups the keys of the same request and reads them at the end of the cycle; `Elm327::read_manufacturer` accepts only services 0x21 and 0x22, only on CAN, adjusts `ATSH`/`ATCRA` (and the flow control when OBDb asks for it) and the next standard request restores the normal addressing (`standard_addressing`). Silence on a manufacturer request counts as a parameter failure (the chosen model may be wrong), not as a frozen adapter. "Verified" depends on the model year (OBDb's `dbg`/`dbgfilter` and files from another generation of the car). The test `maker::tests::obdb_recorded_answers` (ignored by default) checks the decoder against the answers recorded in OBDb's own tests.
- **Bluetooth on Windows.** A Bluetooth COM port is opened only once: the quick speed test (`serial::open_auto`) runs on the same port, because every opening reconnects the radio (seconds) and some clones refuse a second connection right after; and speed does not matter on Bluetooth, so there are no attempts at others. Failures when opening become codes explained on the screen (`port_missing`, `port_busy`, `bt_unreachable`). On BLE, `pick_characteristics` prefers the known services (FFF0, FFE0, 18F0, vLinker, Nordic UART, ISSC), never uses firmware update services, writes to a different characteristic from the one that answers when one exists (FFF2, not FFF1) and, if the write without response fails, switches to the acknowledged one.
- **Windows details.** `transport/bt_ports.rs` reads from the registry (read-only) which Bluetooth COM ports are outgoing (the ones that work) and the adapter's name; `list_ports` puts them first and marks the incoming ones as `bluetooth_in`. `awake.ts` calls `keep_awake`, which uses `SetThreadExecutionState` on the main thread while there is reading, recording or the HUD.
- **Recording with a safety copy.** `recorder.rs` keeps the recording in memory (exporting and playing back is immediate), in a compact way: parameter names are stored only once and each reading stores only the numbers (`session::Values`, about 270 bytes per reading with 30 parameters, some 7 times less than a map; 24 hours fit in about 200 MB) and, at the same time, writes one JSON line per reading to `gravacao-em-andamento.jsonl` (the app's data folder or the portable folder), flushed to disk at least every minute. Each event marked by the user (the **Mark event** button or the Space key) becomes a `{"mark":t_ms}` line and goes to `Session.marks`; the CSV gets a `mark` column. At the start and at the stop, `src/recording-diagnostics.ts` reads the vehicle, trouble codes, freeze frame, readiness and Mode 06 (at the end, only codes and readiness) and sends everything to the `add_recording_diagnostics` command, which stores it in `Session.diagnostics` (a list of `session::Snapshot`) and writes a `{"diagnostics":{...}}` line in the safety copy; readings that finish after the end of the recording still go to it (identified by the start time). The diagnostic report is only generated on request: `recording_report` uses `report::RecordingReport::from_session` (minimum, average and maximum per parameter; hints from the whole trip, re-evaluating the rules of `interpret.rs` at every second of recording; charts with at most 600 points, keeping peaks) and `src/views/report.ts` builds the HTML. A `{"end":true}` line marks the end; without it, `Recorder::recover` brings the recording back the next time the program opens (a line cut by the crash is ignored).
- **Black box.** `obd_core::blackbox` is pure logic, tested without an adapter: `BlackBox` keeps the last 2 min of readings (`PRE_MS`) and, on a trigger, joins those frames to the ones of the next 2 min (`POST_MS`); another trigger within that time stretches the same clip up to `MAX_CLIP_MS` (10 min). `FaultWatch` tells new faults from the ones the car already had: the first read of the lists only learns the existing codes; afterwards a new code in 03/07 becomes `dtc_stored`/`dtc_pending` (once per connection) and the light turning on without a new code becomes `mil`. In `worker.rs`, `FaultChecks` runs between reading cycles: 01 01 every 5 s (light + number of codes), 07 every 30 s, and 03 + 07 only when something changes; a request refused 3 times in a row is not asked again, and every answer goes through `health` (a dropped link is still noticed). On a fault it also reads 0A and the freeze frame (02) and keeps everything as a `Snapshot` in the clip and, if the user is recording, in their recording too, with `Recorder::event` (mark + `Session.events`, an `{"event":{...}}` line in the safety copy). `src-tauri/src/blackbox.rs` turns the clip into a `Session` (`automatic: true`) and writes `falha-<time>-<code>.json` to `gravacoes-automaticas/` (temporary file + rename), deletes the oldest past 30 files or 200 MB (the ones pinned in `fixadas.json` are left out of the count) and tells the interface with the `blackbox` event. In the interface, `src/blackbox.ts` keeps the setting, adds `ESSENTIAL_KEYS` (in `store.ts`) to the reading and shows the notices; `alerts.ts` can trigger the black box (`blackbox_alert`, at most every 10 min per parameter). The simulator creates a new fault with `ATSIMDTC`.
- **Profiles and units only in the interface.** The core always works in metric units (those of the OBD2 standard). `units.ts` converts only for display and when typing limits; `prefs.ts` stores the profiles (fuel, engine size, alerts, VIN); `fuels.ts` calculates the air/fuel ratio and the density of each fuel from the legal blend, weighted by mass, so a change in the law only needs a new number there. The fuels are separated by region (Brazil: E32, E25, hydrous ethanol, B15; USA: E10 regular/midgrade/premium, E15, E85, E0, diesel up to B5, B20; Europe and UK: E10, E5, E85, diesel B7, HVO100, LPG). The region follows the language (`LANG_FUELS` in `unit-presets.ts`) and can be changed in Settings; on changing, `setFuelRegion` (in `prefs.ts`) moves each profile to the fuel with the same role in the new region (regular gasoline → regular E10 → E10…), without deleting profiles or prices. Prices are stored per fuel and the currency comes from the region (`CURRENCY` in `cost.ts`). `prefs.ts` also picks the profile by VIN when connecting. Performance results carry the `profileId`.
- **Read-only guaranteed in the code.** The AT Terminal passes every line through `safety::check_terminal_command` and sends `safety::normalize` (visible ASCII only, so a line never carries a second command after a CR); AT commands that write to the adapter and services that write, test parts or restart control units are refused before leaving the program. `ATCAF0` is also refused (without CAN's automatic formatting, a write request would pass as a read). `Elm327::clear_dtcs` asks for RPM (010C) and speed (010D) on the spot and refuses (`ObdError::Refused("engine_running")`) with the engine turning or the car moving, or (`"engine_unknown"`) if the car does not answer; the screen reads the codes again after clearing. In the simulator, `ATSIMOFF`/`ATSIMON` turn the virtual engine off and on. An AT that changes the configuration (`safety::changes_adapter_setup`: everything except readings like `ATI`, `ATRV`, `ATDP`) marks the state, and when leaving the Terminal the screen calls `restore_adapter`, which runs `Elm327::reconfigure`.
- **Texts outside the Rust code.** The core returns keys (`coolant_temp`, `mixture_lean_b1`) and the interface translates. DTC descriptions are in `crates/obd-core/data/dtc_descriptions.json` (pt and en).
- **Derived calculations in the interface.** Consumption (`trip.ts`; the instantaneous consumption also becomes the calculated parameters of `calc.ts`, which the Charts screen draws like the car's own), performance tests (`perf.ts`, pure logic tested with Vitest), guided tests (`battery.ts`, `o2test.ts` and `trims.ts`, also pure logic: steps, limits and evaluation; the `views/guided.ts` screen only draws and asks the worker to read just the test's values), alerts (`alerts.ts`) and playback of recordings (`playback.ts`) use the same live frames as the dashboard; that is why they work the same with the car and with a recording. The interpretation during playback uses the same Rust code (`interpret_frames`).
- **Mode 06 hints** (`mode06hints.ts`, pure logic tested with Vitest): reads the list of control unit tests already received and points out known patterns (misfire in one cylinder, catalytic converter, sensors). The `views/diagnostics.ts` screen only shows the result.
- **Trips of the Trip screen in IndexedDB.** A long trip has thousands of lines (one per second), too many for `localStorage`. `journey-store.ts` keeps the list (small) and the lines (large) in two stores of WebView2's IndexedDB, in the same data folder as the program (or the portable one). `journey-live.ts` adds the trip's parameters to what the adapter reads (`readKeys` in `store.ts`), writes one line per second with the trip computer's consumption and saves every 30 s; an open trip continues when the program opens again. The analysis (`journey.ts`) is pure logic, tested with Vitest, and works the same for live trips and recordings; it also cuts stretches (`applyCuts`, without deleting the data) and compares two trips (`compare`, `winner`, `advantage`). The pre-trip check (`precheck.ts`, pure logic) evaluates codes, check engine light, battery or alternator and temperature; the screen reads these values for a few seconds with `state.extraKeys` and gives the reading back as it was.
- **Nothing loaded from the internet.** The chart (uPlot), the Markdown reader (marked) and the diagram drawer (Mermaid) are packaged in the app; the security policy (CSP) blocks external sources.
- **Embedded documentation.** `src/docs.ts` imports `README.md` and the `docs/*.md` files as text (Vite's `?raw`), together with their English copies in `docs/en/`, and the newest release notes (`import.meta.glob`); `views/docs.ts` shows them with `marked` (HTML inside Markdown becomes text, never executed) and draws the `mermaid` blocks with `securityLevel: "strict"`, loading Mermaid only when needed (dynamic import, in a separate file). The screen shows the version in the program's language: pt-BR uses the Portuguese originals, en-US the English copies and en-GB the same English copies with British spelling (`british()` from `locales/en-GB.ts`, applied outside code and links). The section ids follow GitHub's rule, so the same links work on the website and in the program. The project rules live in [REGRAS-DO-PROJETO.md](REGRAS-DO-PROJETO.md).

## Tests

Running: `cargo test -p obd-core --all-features` (core; a `cargo test` without `-p` tries to compile the whole Tauri app, which on Linux asks for WebKit/GTK) and `npm test` (interface).

- `crates/obd-core/src/*`: connection health tests (`health.rs`), formulas, DTC, VIN, readiness, interpretation, CSV/JSON.
- `crates/obd-core/tests/elm327_integration.rs`: a full session against the simulator (normal and clone), recovery of a frozen, restarted, hung and dropped adapter, and recorded answers from real adapters (a clone without `OK`, ignition off, ISO 9141 protocol with two control units, `STOPPED`/`BUFFER FULL`, refused AT commands, Mode 06, fast reading).
- `src/units.test.ts` (Vitest): unit conversion, values inside texts and switching units together with the language.
- `src/locales.test.ts` (Vitest): the three languages have the same texts and `{...}` markers, no Portugal words in pt-BR, no British spelling in en-US and no American spelling in en-GB.
- `src/battery.test.ts` (Vitest): battery test with simulated voltages (healthy car, unstable voltage, engine on in step 1, start not seen, smart charging).
- `src/o2test.test.ts` (Vitest): sensors with simulated signals (good and worn catalytic converter, stuck sensor, slow adapter, wide-band sensor).
- `src/trims.test.ts` (Vitest): trim map (bands, open loop ignored, reserve by temperature, air intake patterns, lack of fuel, lean everywhere, purge).
- `src/presets.test.ts` and `src/warmup.test.ts` (Vitest): ready-made panels and chart presets (only what the car reports, alternatives) and the cold/ready engine badge.
- `src/calc.test.ts` (Vitest): which of the car's parameters each calculated value depends on.
- `src/cost.test.ts` (Vitest): trip cost, gasoline × ethanol comparison by energy and the price of the blend in flex.
- `src/docs.test.ts` (Vitest): embedded documents, section ids equal to GitHub's, links between documents pointing to sections that exist, and the Portuguese and English documents having the same structure.
- `src/search.test.ts` (Vitest): global search (accents and capitals ignored, all the words, title counts more than description, trouble codes).
- `src/drives.test.ts` (Vitest): trip history (groups by fuel, flex by ethanol percentage, averages by total distance, short trips without an average, monthly totals, the car's usual average).
- `src/journey.test.ts` (Vitest): analysis of the Trip screen (distance, liters and consumption by stopped/city/road, gaps without data, a car without consumption data, tips on idling and high speed, hard accelerations and braking, engine braking and high RPM, engine warm-up, mixture only in closed loop, comparison with the average, chart series, conversion of a recording, cuts and comparison of two trips).
- `src/precheck.test.ts` (Vitest): pre-trip check (stored and pending codes, check engine light, battery with the engine off, alternator with the engine on, smart charging, overcharging, hot engine).
- `src/summary.test.ts` (Vitest): trip summary (stopped and moving time, distance, peaks, alerts, short trips ignored, reading failures, connection ended).
- `src/trips.test.ts` and `src/refuel.test.ts` (Vitest): Trip A and Trip B (start, pause, reset, average speed) and calibration from refueling (short stretches, reading failures, out-of-range result, average of the last 5).
- `src/fuels.test.ts` (Vitest): air/fuel ratio and density of each region's blends and the switch to the equivalent fuel when the region changes.
- `src/mode06hints.test.ts` (Vitest): Mode 06 hints (misfire per cylinder, catalytic converter, sensors).
- `src/report.test.ts` (Vitest) and `crates/obd-core/src/report.rs`: report from a recording (with and without codes and readiness).
- `src/perf.test.ts` (Vitest): detection of the performance tests with simulated speed profiles (launch, rolling acceleration, braking, giving up, reading failure, slow adapter).
- CI (`.github/workflows/ci.yml`): tests on Linux and building the installer on Windows.

## How to add

> When you create, change or remove a component, also update [DIAGRAMAS.md](DIAGRAMAS.md) in the same commit.

- **A parameter (PID):** a line in `PIDS` (`pid.rs`) + texts in `src/locales/*.ts` (`pids`).
- **A model with manufacturer parameters:** clone the model's repository from OBDb, add it to `MODELS` (`tools/obdb_import.py`), run the script and translate the names it lists in `tools/obdb_names_missing.txt` (into `tools/obdb_names_pt.tsv`).
- **A trouble code:** an entry in `dtc_descriptions.json`.
- **A document for the Documentation screen:** the file in `docs/` and its English copy in `docs/en/` (same name), a line in `DOCS` (`src/docs.ts`) and a title/description in `docs.list` (`src/locales/pt-BR.ts` and `en-US.ts`).
- **A theme:** a `:root[data-theme="name"]` block in `styles.css`, preview colors in `THEME_SWATCH` (`theme.ts`) and name/description in `settings.themes`.
- **A unit:** a case in `conversion()` (`units.ts`), an option in `UNIT_CHOICES` and a name in `units.names`.
- **A language:** copy `src/locales/en-US.ts`, translate it, register it in `LANGS` (`src/i18n.ts`) and say which units it uses in `LANG_UNITS` (`src/unit-presets.ts`); translate the documents too (`docs/<code>/`) and add them to `src/docs.ts`. English (Europe) (`en-GB.ts`) is generated from `en-US.ts` by the `british()` function; texts with different words go in `OVERRIDES` in the same file.
- **Values with units in texts:** write them in metric (`60 °C`, `{km} km`, `~101 kPa`). `convertUnitsIn()` (`units.ts`) converts when displaying. Texts that must stay metric (unit names, names of the performance tests) are in `KEEP_UNITS` (`i18n.ts`).
